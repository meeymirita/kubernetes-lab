## 1.1 Проблема: когда контейнеров становится сотня | short: Зачем оркестратор | est: ~25 мин
### intro
**Слова шага:** *оркестратор*, *самолечение (self-healing)*, *масштабирование*, *обновление без простоя*, *декларативность*.

:::tip Если совсем просто
`docker compose up -d` отлично работает, пока сервисов десять и они живут на одной машине, которую обслуживаешь ты сама. А если копий API должно быть пятнадцать, разбросанных по пяти машинам, и ночью одна из машин выключилась? Руками — не успеешь. Оркестратор — это **автопилот для контейнеров**: ты говоришь «я хочу 15 копий API, 3 ГБ памяти на каждую», а он сам решает, на какой машине их запустить, и сам перезапускает упавшие.
:::

В Docker- и Traefik-лабах мы управляли контейнерами **императивно**: `docker compose up`, `docker restart`, `docker compose down`. Это нормально, пока:

- всё крутится **на одной машине** (упала машина — упало всё);
- копий сервиса немного, и их можно пересчитать на пальцах;
- обновление версии — это «погасить и поднять заново», короткий простой тебя не пугает;
- следишь за здоровьем контейнеров ты сама, глазами.

На практике у растущего проекта это ломается. Три конкретные ситуации:

1. **Машина с API упала в 3 ночи.** Никто не перезапустил сервис — сайт недоступен до утра.
2. **Чёрная пятница.** Нагрузка выросла в 10 раз — нужно быстро поднять ещё 10 копий API и потом так же быстро их убрать, чтобы не платить за простаивающие машины.
3. **Нужно выкатить новую версию API 50 раз в месяц** — без заметного для пользователей простоя, и с возможностью мгновенно откатиться, если что-то пошло не так.

Все три решаются одной идеей: **декларативность**. Вместо «выполни эти команды» ты пишешь «вот как должно быть» (манифест: «3 копии API, образ такой-то, доступен через вот такой Service») и отдаёшь его **оркестратору**. Он сам:

- постоянно сверяет **желаемое состояние** (что написано в манифесте) с **текущим** (что реально работает) — и устраняет разницу (это называется *reconcile*, подробно — сессия 2);
- перезапускает упавшие контейнеры без твоего участия (*self-healing*);
- переносит их на другую машину, если одна из машин отказала;
- может сам добавлять и убирать копии по нагрузке (сессия 10).

**Kubernetes** — самый распространённый оркестратор; **Helm** — менеджер пакетов для него (сессия 12), который упаковывает группу манифестов в переиспользуемый «набор».

### result
Запускать здесь нечего — это шаг-мотивация. Но запомни формулировку, которая будет направлять всю лабу: **ты описываешь желаемое состояние, кластер сам приводит реальность к нему.** Каждый раз, когда что-то «не работает так, как я написала», вопрос не «что мне сделать руками», а «что в моём манифесте не совпадает с тем, что я хочу».

### why
Переход от императивного управления к декларативному — это смена привычки, не только инструмента. Самая частая ошибка новичков в Kubernetes — пытаться «поправить руками в кластере» (как делали в Docker) вместо правки манифеста. Это проходит без следа до первого пересоздания Pod — и тогда правка исчезает. Привыкай сразу: **правь файл, потом `apply`.**

### deep Чем это отличается от Docker Swarm
Docker Swarm — более простой оркестратор, встроенный в сам Docker: декларативность и самолечение там тоже есть, но меньше возможностей (нет PersistentVolumeClaim в современном виде, нет такого богатого Ingress/CRD-экосистемы, сообщество меньше). Если тебе хватало Swarm — многие идеи (сервис, реплики, роллинг-обновление) будут знакомы, Kubernetes просто детальнее на каждом шаге.

### deep Если прямо сейчас не укладывается в голове, зачем это всё
Держи в голове только одну картинку из этого шага: «ночью упала машина — сайт сам поднялся без тебя». Остальное — детали того, как это устроено. Если к концу сессии 4 (Deployment) эта картинка не станет понятнее — вернись и перечитай этот шаг.

## 1.2 Что такое Kubernetes и Helm | short: Kubernetes и Helm | est: ~30 мин
### intro
**Слова шага:** *кластер*, *узел (node)*, *control plane*, *worker-узел*, *Pod*, *манифест*, *chart*.

:::tip Если совсем просто
Kubernetes — это **кухня ресторана с управляющим**: управляющий (control plane) не готовит сам, он читает заказы (манифесты) и раздаёт их поварам (worker-узлам), следит, что каждый заказ выполнен, и заменяет повара, если тот не вышел на смену. Helm — это **книга готовых рецептов с заменяемыми ингредиентами**: вместо того чтобы писать соус, тесто и начинку по отдельности каждый раз, ты берёшь рецепт («chart») и говоришь «но соус поострее» (`values.yaml`).
:::

**Kubernetes** — система, которая управляет контейнерами на группе машин (*кластер*) как единым целым:

- **Кластер** состоит из **узлов** (*node*) — отдельных машин (или виртуальных машин, или, как в нашем случае, Docker-контейнеров, которые *притворяются* машинами).
- Один тип узлов — **control plane**: «мозг» кластера, принимает манифесты, решает, что и где запускать, следит за состоянием. Подробно — сессия 2.
- Другой тип — **worker-узлы**: туда реально попадают твои контейнеры (упакованные в **Pod**, сессия 3).
- Ты описываешь желаемое в **манифестах** — текстовых файлах в формате YAML — и отдаёшь их кластеру командой `kubectl apply`.

**Helm** — отдельный инструмент (не часть самого Kubernetes), который решает другую задачу: у сложного приложения манифестов становится десять-двадцать, и в них повторяются одни и те же версии, адреса, метки. Helm **упаковывает** набор манифестов в **chart** с шаблонами и одним файлом настроек (`values.yaml`), чтобы поставить всё приложение одной командой и для разных окружений (dev/prod) менять только значения, а не переписывать манифесты. Подробно про Helm — сессии 12–15; до тех пор мы пишем манифесты руками, чтобы понимать, что именно Helm потом упаковывает.

**Чем это отличается от того, что ты знаешь.**

| | Docker Compose | Docker Swarm | Kubernetes |
|---|---|---|---|
| Одна машина или кластер | обычно одна | кластер | кластер |
| Самолечение | нет (`restart: unless-stopped` — это не то же самое) | есть | есть, детальнее |
| Автомасштабирование по нагрузке | нет | ограниченно | есть (HPA, сессия 10) |
| Формат описания | `compose.yaml` | `compose.yaml` (стек) | манифесты YAML (Pod, Deployment, Service…) |
| Экосистема готовых «рецептов» | нет | нет | Helm charts, тысячи готовых |

### result
Пока ничего не запускаем — закрепим словами: **узел** — машина, **Pod** — наименьшая единица развёртывания (сессия 3), **манифест** — файл с желаемым состоянием, **chart** — упакованный набор манифестов. Эти четыре слова встретятся в лабе ещё множество раз.

### why
Путаница «Kubernetes vs Helm vs Docker» у новичков обычно сводится к одному: Kubernetes — это **среда выполнения и API**, а Helm — **инструмент поверх неё**, который сам ничего не выполняет, а только генерирует и применяет те же манифесты. Если Helm «ломается» — почти всегда проблема в сгенерированном YAML, а не в самом Kubernetes.

### deep Откуда взялось название
Kubernetes (от греч. «кормчий», тот, кто управляет кораблём) — открытый проект, выросший из внутренней системы Google (Borg). Отсюда и логотип (штурвал), и то, что многие термины («Pod» — стручок, группа «горошин»-контейнеров) — морская и биологическая метафора, не случайный набор слов.

### deep Что ещё называют «оркестрацией»
Nomad (HashiCorp), Apache Mesos, управляемые варианты в облаках (EKS, GKE, AKS) — это тот же Kubernetes API под капотом, просто control plane обслуживает облачный провайдер, а не ты. Всё, что ты учишь в этой лабе на `kind`, работает так же в проде — набор команд не меняется.

## 1.3 Минимум Docker и проверка `starter/` | short: Проверка starter | est: ~30 мин
### intro
**Слова шага:** *образ*, *registry*, *слои образа*, *совместимость стартовой папки*.

:::tip Если совсем просто
Прежде чем переезжать на новую квартиру (Kubernetes), проверим, что вещи из старой (образ API, манифесты Traefik) целы и упакованы правильно — иначе будем переносить мебель, которой на самом деле нет.
:::

Вся лаба продолжает стек из Traefik-лабы. Если у тебя его нет — скачай/скопируй `starter/` (см. README лабы) и начни с этого шага; если есть — проверим его целостность.

```bash run
cd ~/traefik-lab/starter 2>/dev/null || cd ~/kubernetes-lab/starter
ls coffeeshop/api coffeeshop/web coffeeshop/db edge 2>&1
cat coffeeshop/api/Dockerfile | head -5
docker build -t coffeeshop-api:v1 ./coffeeshop/api 2>&1 | tail -5
docker images coffeeshop-api
```

### result
```out auto
```

Три вещи должны быть на месте: папка `coffeeshop/api` с `Dockerfile` (обычный многослойный образ Node.js — слой с зависимостями кэшируется отдельно от слоя с кодом, это ты уже видела в Docker-лабе), папка `coffeeshop/web` со статикой фронтенда, и `coffeeshop/db/init.sql` для PostgreSQL. Образ собрался и называется `coffeeshop-api:v1` — именно под этим именем мы будем грузить его в кластер `kind` в шаге 3.6.

Напомним минимум, который нужен дальше по лабе: **образ** — неизменяемый «слепок» файловой системы и команды запуска; **слои** — он собирается послойно, и совпадающие слои между образами не копируются повторно; **registry** — хранилище образов (Docker Hub, GHCR…), из которого их можно скачать `docker pull`. В Kubernetes узел тоже должен **скачать** образ, прежде чем запустить контейнер — и в этом есть нюанс с локальным кластером, который мы разберём в шаге 3.6 (`kind load docker-image`: у кластера нет доступа к твоему локальному Docker, образ нужно явно туда «занести»).

### why
Самая частая причина «ничего не работает» в первых сессиях Kubernetes — вообще не про Kubernetes, а про то, что образ приложения не собрался или называется не так, как в манифесте. Проверить это *до* того, как начать разбираться в Pod, экономит часы.

### deep Если `starter/` нет совсем
Прочитай `edge/README.md` (если он есть в твоей копии) или собери минимальную замену: Node.js-сервис с `/health`, который отвечает `200 OK`, — для первых сессий (1–4) этого достаточно, полноценный `starter/` понадобится начиная с сессии 5 (Ingress) и особенно 6 (PostgreSQL).

### deep Если нет Traefik-лабы вообще
Это нормально (режим «самостоятельная»): нужен только сам код приложения, механизм Traefik (метки) в манифесты переводить не из чего — просто начни с Ingress с нуля в сессии 5, пропустив сравнение «как было у Traefik».

## 1.4 Инструменты: kubectl, kind, helm | short: Инструменты | est: ~30 мин
### intro
**Слова шага:** *`kubectl`*, *`kind`*, *`helm`*, *автодополнение*, *YAML-плагин редактора*.

:::tip Если совсем просто
`kubectl` — пульт управления кластером (одна команда — один «клик» по кнопке). `kind` — коробка, в которой мы соберём сам «телевизор» (кластер) из обычных Docker-контейнеров. `helm` — каталог готовых программ для этого телевизора, которые ставятся одной кнопкой.
:::

Три инструмента, их нет ни в Docker-, ни в Traefik-лабе — ставим впервые. На Mac — через Homebrew:

```bash run
brew install kubectl kind helm
kubectl version --client
kind version
helm version
```

### result
```out auto
```

- **`kubectl`** — CLI-клиент, который говорит с API любого кластера Kubernetes (локального `kind` или настоящего облачного — команды одни и те же).
- **`kind`** (*Kubernetes IN Docker*) — инструмент, который поднимает **настоящий** кластер Kubernetes, но каждый узел — это Docker-контейнер на твоей машине, а не отдельная виртуалка. Для обучения и локальной разработки — основной выбор.
- **`helm`** — CLI для Helm; сам по себе ничего не делает, пока мы не начнём сессию 12.

**Автодополнение** (чтобы не печатать длинные имена ресурсов целиком):

```bash
echo 'source <(kubectl completion zsh)' >> ~/.zshrc
echo 'source <(helm completion zsh)' >> ~/.zshrc
source ~/.zshrc
```

**Редактор.** В VS Code поставь плагин «YAML» (Red Hat) — он подключает схемы Kubernetes и подсказывает поля прямо при наборе, подчёркивая опечатки (`replicas` вместо `replica`) ещё до `kubectl apply`.

### why
YAML Kubernetes не прощает неверных отступов и имён полей так же, как не прощал `docker-compose.yaml`, но ошибок здесь больше: у объекта может быть 20+ допустимых полей. Плагин редактора и `kubectl explain` (следующий шаг) экономят время с первого дня.

### deep Как ещё можно (не Mac/Homebrew)
- **Linux:** `curl -LO` бинарников с официальных страниц релизов каждого инструмента, либо пакетный менеджер дистрибутива.
- **Windows:** `choco install kubernetes-cli kind kubernetes-helm` (Chocolatey) или через `winget`.
- **Без установки на хост:** образ `bitnami/kubectl` или алиас, который гоняет `kubectl` в одноразовом контейнере, — неудобно для ежедневной работы, но вариант для CI.

### deep Если не получилось
- **`brew: command not found`** — Homebrew не установлен: `https://brew.sh`.
- **`kind version` нашёлся, но слишком старая версия** — `brew upgrade kind`; нам нужен v0.33 или новее (для образа узла v1.37).
- **Долго качается `kubectl version --client`** — у новых версий `kubectl` эта команда по умолчанию ничего не качает, но если видишь паузу — проверь интернет, не влияет на дальнейшую работу.

## 1.5 Локальный кластер: `kind create cluster` | short: Создаём кластер | est: ~40 мин
### intro
**Слова шага:** *конфиг кластера*, *`extraPortMappings`*, *контекст*, *`kubeconfig`*.

:::tip Если совсем просто
`kubeconfig` — это записная книжка с адресами всех кластеров, с которыми ты когда-либо работала, и твой текущий «выбранный номер» в ней — контекст. `kubectl` всегда звонит по тому номеру, что выбран сейчас — если перепутала, команды уходят не туда (или никуда).
:::

```svg
@cluster-anatomy
```

По умолчанию `kind create cluster` поднимает один узел (control plane и worker — в одном). Нам для реалистичности нужно отдельно: 1 control-plane + 2 worker-узла, и сразу настроим `extraPortMappings` — проброс портов 80/443 с хоста прямо в кластер (без него доступ к Ingress в сессии 5 был бы неудобным).

```bash run
mkdir -p ~/kubernetes-lab && cd ~/kubernetes-lab
cat > kind-config.yaml <<'EOF'
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
name: coffeeshop
nodes:
  - role: control-plane
    extraPortMappings:
      - containerPort: 80
        hostPort: 80
      - containerPort: 443
        hostPort: 443
  - role: worker
  - role: worker
EOF
kind create cluster --config kind-config.yaml --image kindest/node:v1.37.0
kubectl cluster-info
kubectl config current-context
kubectl get nodes -o wide
```

### result
```out auto
```

Что произошло: `kind` подняла три Docker-контейнера (`coffeeshop-control-plane`, `coffeeshop-worker`, `coffeeshop-worker2` — проверь `docker ps`), внутри каждого — настоящий Kubernetes (`kubelet`, `containerd` и так далее, сессия 2). `kubectl cluster-info` показывает адрес API-сервера control-plane. `kubectl config current-context` — записная книжка `~/.kube/config` автоматически получила новую запись `kind-coffeeshop` и переключилась на неё: это и есть **контекст**. `kubectl get nodes` — три узла в статусе `Ready` (может занять до минуты: сетевой плагин должен подняться первым).

**Про `extraPortMappings`.** Порты 80/443 на твоём Mac теперь ведут внутрь кластера, на control-plane-узел. Это заменяет настоящий облачный `LoadBalancer`, которого у локального `kind` нет (сессия 5 объясняет это подробно).

### why
Контекст — источник самой коварной путаницы у новичков: команда «не видит» ресурс не потому, что он не создан, а потому, что `kubectl` смотрит в **другой** кластер (например, остался контекст от предыдущей лабы или облачного аккаунта). Привычка проверять `kubectl config current-context` перед непонятной ошибкой экономит массу времени.

### deep Команды по частям
`kind create cluster --config kind-config.yaml --image kindest/node:v1.37.0`: `--config` — файл с описанием узлов (без него был бы один узел); `--image` — фиксирует версию Kubernetes внутри узлов (без неё `kind` ставит свою последнюю проверенную, которая может не совпасть с планом лабы). `kubectl get nodes -o wide` — `-o wide` добавляет IP-адреса и версию `kubelet`/ОС по сравнению с обычным `get nodes`.

### deep Если не получилось
- **Узлы долго в `NotReady`** — нормально до минуты: сетевой плагин (CNI) разворачивается последним; если дольше трёх минут — `kubectl get pods -n kube-system` и смотри, что не стартовало.
- **`failed to create cluster: node(s) already exist for a cluster with the name "coffeeshop"`** — кластер с таким именем уже есть: `kind delete cluster --name coffeeshop`, потом создать заново.
- **Порт 80 занят** — у тебя, вероятно, работает Traefik-лаба или Caddy-лаба: останови их стенд (`docker compose down` в соответствующей папке) или поменяй `hostPort` на свободный (тогда адреса из сессии 5 придётся открывать с этим портом).

## 1.6 YAML и структура манифеста | short: YAML и манифест | est: ~35 мин
### intro
**Слова шага:** *`apiVersion`*, *`kind`*, *`metadata`*, *`spec`*, *`kubectl explain`*.

:::tip Если совсем просто
Любой манифест Kubernetes — это анкета с четырьмя графами: «по какому бланку» (`apiVersion`), «какая это анкета» (`kind`), «кто подаёт» (`metadata`: имя, метки), «что хочу» (`spec`). Не помнишь, какие поля можно заполнить в разделе — не гугли, спроси саму анкету: `kubectl explain`.
:::

Любой манифест — YAML-документ из четырёх верхнеуровневых полей:

```yaml
apiVersion: v1          # версия API-группы, которой принадлежит этот тип объекта
kind: Pod                # тип объекта: Pod, Deployment, Service, ConfigMap...
metadata:                # «паспорт»: имя, namespace, labels, annotations
  name: example
spec:                    # желаемое состояние — своё для каждого kind
  containers: []
```

`kubectl explain` — встроенная документация, читает её прямо из API кластера (значит, всегда соответствует установленной версии Kubernetes, в отличие от гугла):

```bash run
kubectl explain pod.spec --recursive | head -20
kubectl explain pod.spec.containers.resources
```

### result
```out auto
```

`kubectl explain pod.spec --recursive` печатает дерево всех допустимых полей внутри `spec` у `Pod` — это таблица полей без похода в документацию. `kubectl explain pod.spec.containers.resources` — то же самое для одного конкретного поля с описанием, что оно делает (нам это понадобится в сессии 8 для `requests`/`limits`).

### why
У новичка два врага: опечатка в имени поля (YAML её не ловит — непонятное поле просто игнорируется или API вернёт ошибку валидации) и путаница версий API (`apps/v1` для `Deployment`, но `v1` для `Pod` и `Service` — группы разные). `kubectl explain` решает оба: показывает именно то, что понимает твой кластер прямо сейчас.

### deep Отступы — не косметика
YAML использует **только пробелы** для вложенности (никогда табы), и количество пробелов — само содержание структуры: `containers:` на уровень глубже, чем `spec:`, значит, он внутри `spec`. Сдвинь строку на один пробел не туда — получишь либо ошибку парсинга, либо (хуже) тихо другую структуру, которая не делает то, что ты хотела.

### deep Если не получилось
- **`error: unable to recognize ".../x.yaml": no matches for kind "..." in version "..."`** — опечатка в `kind` или `apiVersion` не соответствует тому, что умеет кластер; сверь с `kubectl api-resources` (сессия 2.5).
- **`kubectl explain` ругается «couldn't find resource»** — опечатка в имени ресурса или поля; начни с `kubectl explain pod` и спускайся по дереву (`pod.spec`, `pod.spec.containers`…).

## 1.7 Организация каталога проекта | short: Структура проекта | est: ~20 мин
### intro
**Слова шага:** *структура манифестов*, *`kustomization` (вперёд забегая)*, *именование файлов*.

:::tip Если совсем просто
Пока манифестов пять — любая организация работает. Когда их пятьдесят (а к сессии 15 у нас будет похожий масштаб), находить нужный файл по имени «как в книге с главами» экономит реальное время.
:::

Договоримся о структуре каталога на всю лабу (создавать все папки заранее не нужно — появятся по ходу):

```text
~/kubernetes-lab/
├── kind-config.yaml       # сессия 1
├── manifests/
│   ├── 01-pod-api.yaml     # сессия 3
│   ├── 02-deployment-api.yaml   # сессия 4
│   ├── 03-service-api.yaml
│   ├── 04-ingress.yaml     # сессия 5
│   ├── 05-pvc-db.yaml      # сессия 6
│   ├── 06-configmap.yaml   # сессия 7
│   ├── 06-secret.yaml
│   └── ...
├── chart/                  # сессия 12+, Helm chart CoffeeShop
└── starter/ -> ~/traefik-lab/starter   # ссылка на итог Traefik-лабы
```

Нумерация в начале имени файла — не формальность: `kubectl apply -f manifests/` применяет файлы из папки в алфавитном порядке, и если Service должен существовать раньше, чем на него сошлётся Ingress, порядок имён избавляет от части ошибок «ресурс ещё не создан». В сессии 15 мы заменим ручной порядок на честные зависимости Helm.

### result
Структуры для запуска команд здесь нет — просто договорённость об именах, которой лаба будет держаться дальше. Если тебе удобнее своя — веди её последовательно, в тексте методички дальше имена файлов будут ориентиром, а не жёстким требованием.

### why
Хаос в именах манифестов — одна из причин, почему «работало вчера, не работает сегодня»: приложила не тот файл, забыла, что Service лежит в другом месте. Привычка к порядку окупается уже на сессии 4–5.

### deep Как это выглядит в проде
В реальных проектах манифесты почти всегда лежат в git, часто разбиты по `kustomize`-оверлеям (`base/` + `overlays/dev,prod`, сессия 15) или сразу как Helm chart (сессия 12+). Ручная папка `manifests/` — учебный шаг к этому.

## 1.8 🔨 `connection refused`: кластер не там | short: 🔨 connection refused | est: ~30 мин
### intro
**Слова шага:** *`connection refused`*, *неверный контекст*, *кластер не поднят*.

:::tip Если совсем просто
`kubectl` звонит по записанному номеру (контексту). Если номер верный, но трубку не берут — кластер выключен. Если номер неверный — ты вообще звонишь не туда, а ошибка выглядит одинаково пугающе в обоих случаях.
:::

Сломаем специально: остановим кластер, не удаляя его, и посмотрим на типичную ошибку.

```bash run
docker stop coffeeshop-control-plane >/dev/null
kubectl get nodes
```

### result
```out auto
```

Типичный текст: `The connection to the server 127.0.0.1:PORT was refused - did you specify the right host or port?`. Два диагностических вопроса по порядку:

**1. Верный ли контекст?**

```bash run
kubectl config current-context
kubectl config get-contexts
```

Если контекст — не `kind-coffeeshop` (например, остался от другой лабы или от аккаунта в облаке), команда `kubectl config use-context kind-coffeeshop` переключит её на нужный.

**2. Если контекст верный — жив ли сам кластер?**

```bash run
docker ps -a --filter name=coffeeshop
docker start coffeeshop-control-plane >/dev/null
sleep 5
kubectl get nodes
```

### result
```out auto
```

После `docker start` control-plane поднимается заново (это такой же контейнер, как любой другой — `docker start` его не пересоздаёт, только включает), и через несколько секунд `kubectl get nodes` снова отвечает. Если бы контейнера не было вообще (`docker ps -a` не нашёл его) — тогда кластер нужно создавать заново (`kind create cluster`), а не стартовать.

### why
«Connection refused» — это ошибка **транспорта**, не Kubernetes: она значит «я вообще не смогла поговорить с API-сервером», и причина почти всегда одна из двух: не тот адрес (контекст) или адрес верный, но там никто не слушает (кластер не запущен или только разворачивается). Это ровно тот же первый вопрос диагностики, что был в Traefik-лабе про стадии DNS/TCP/TLS/HTTP — только здесь «сервер» — это `kube-apiserver`.

### deep Если не получилось
- **После `docker start` всё равно `connection refused`** — подожди подольше: API-серверу и `etcd` нужно время на запуск; `docker logs coffeeshop-control-plane --tail 20` покажет, на каком этапе он застрял.
- **`kind delete cluster` → `kind create cluster` потерялись все созданные объекты** — это ожидаемо: `kind` не хранит состояние на диске хоста по умолчанию, пересоздание кластера — это новый, пустой кластер.
