Это сессия без новой теории: ты сама собираешь продакшн-релиз CoffeeShop, используя всё пройденное.

**Задача.** Хозяйка кофейни переезжает с одного сервера с Docker Compose на кластер Kubernetes. Дан **чистый кластер `kind`** (по конфигу из шага 1.5, с Traefik из шага 5.4) и код CoffeeShop из `starter/`: API, frontend, PostgreSQL, Adminer. Нужно подготовить **релиз**, который ставится на любой такой чистый кластер одной командой, переживает падение отдельных Pod и обновление, и не требует ручных правок после установки. **Код приложения менять нельзя** — меняется только способ развёртывания.

```svg
@final-task
```

**Требования.** Работай в новой папке: `mkdir ~/kubernetes-lab/final && cd ~/kubernetes-lab/final`. Новый кластер — `kind create cluster --name final --config …`.

**A. Релиз**

1. Весь стек (API, frontend, PostgreSQL, Adminer, Ingress) ставится **одним Helm-релизом** — umbrella chart или несколько chart’ов под одной командой/скриптом (на твой выбор, выбор обоснуй в `README.md`).
2. `helm install` (или `helm upgrade --install`) на чистом кластере поднимает рабочий сайт **без единой правки руками** после установки.
3. Установка и обновление используют `--atomic --wait --timeout`.

**B. Доступность и обновления**

1. API — минимум 2 реплики; обновление образа идёт без простоя (укажи стратегию и объясни выбор значений `maxSurge`/`maxUnavailable`).
2. Пробы `readiness` и `liveness` настроены осмысленно: проверяют реальную способность отвечать, а не просто «порт открыт».
3. Для API задан `PodDisruptionBudget` или обоснование, почему он не нужен на двух репликах (`README.md`).

**C. Данные**

1. PostgreSQL хранит данные на PVC: удаление Pod БД не приводит к потере данных (покажи).
2. Пароль БД — **в Secret**, не открытым текстом в `values*.yaml` и не в Git; способ передачи описан (`README.md`).
3. Резервная копия БД по расписанию (`CronJob` с `pg_dump`) или обоснованный отказ.

**D. Доступ и безопасность**

1. Снаружи доступны только `shop.localhost` (сайт + `/api`) и `adminer.shop.localhost` через Ingress (Traefik); ни один сервис не опубликован через `NodePort`.
2. Контейнеры API и frontend работают **не от root**, без повышения привилегий, с `drop: ["ALL"]`; namespace релиза соответствует Pod Security Standards `restricted` или `baseline` (уровень обоснуй).
3. `NetworkPolicy`: до БД достучаться может **только API** (frontend и Adminer — не могут, если им это не нужно; если Adminer нужен — явно разреши и обоснуй). Проверено командой изнутри Pod, а не по виду объекта.
4. RBAC: минимум одна `Role` + `RoleBinding` с ограниченными правами (например, «только читать Pod релиза»), проверено `kubectl auth can-i --as`.

**E. Масштабирование и наблюдаемость**

1. HPA на API по CPU (от 2 до 5 реплик), у контейнеров заданы `requests`; нагрузочный тест показывает рост числа реплик и возврат к минимуму.
2. У API заданы `requests`/`limits`; в `README.md` объяснено, почему именно такие.
3. Мониторинг: на дашборде (Grafana или `kubectl top`, что выбираешь — обоснуй) видны CPU, память и число готовых реплик API.

**F. Окружения и откат**

1. `values-dev.yaml` и `values-prod.yaml` — разные ресурсы/реплики; показан переход между ними без правки шаблонов.
2. Авария: `upgrade` на неработающий образ откатывается автоматически; ручной `helm rollback` возвращает рабочую версию. Данные БД при этом не потеряны.
3. `helm lint --strict`, `helm template` и `helm test` (хотя бы один тест-Pod) проходят.

**G. Документация**

1. `README.md`: схема релиза (нарисуй сама), как поставить с нуля, как обновить, как откатить, как удалить с сохранением данных, что делать при `Pending`, `CrashLoopBackOff`, `ImagePullBackOff`, `OOMKilled`, `503`.

**Критерии приёмки (самопроверка).** Каждая строка таблицы должна выполняться, и **команду для каждой проверки подбираешь ты сама**:

| Проверка | Ожидаемый результат |
|---|---|
| `kind delete cluster --name final`, новый кластер, одна команда установки | сайт работает, `kubectl get pods -A` без `Error`/`Pending` |
| `curl http://shop.localhost/` и `…/api/health` | `200` |
| `curl http://adminer.shop.localhost/` | `200` |
| удалить Pod API (`kubectl delete pod …`) | запросы продолжают идти без ошибок |
| удалить Pod БД | данные заказов на месте после его возвращения |
| `kubectl auth can-i delete pods --as=…` | `no` у ограниченной роли, `yes` у разрешённой |
| запрос к БД из Pod frontend | таймаут |
| запрос к БД из Pod API | успешно |
| нагрузка на API | число реплик растёт, затем падает |
| `helm upgrade` на `image.tag=нет-такого` | автоматический откат, сайт работает |
| `helm history`, `helm rollback` | ревизии видны, откат проходит |
| `helm lint --strict`, `helm test` | без ошибок |
| поиск пароля БД по файлам в папке `final/` (`grep -r`) | не находится |

**Чего не требуется:** настоящего домена и TLS от Let’s Encrypt, внешнего LoadBalancer, автоскейлера узлов, GitOps, облака, собственных метрик в приложении.

**Порядок работы (подсказка, не решение):** сначала chart для БД и Secret; потом API и проверка связи; потом frontend и Ingress; потом пробы и ресурсы; потом `securityContext` и namespace с политикой; потом `NetworkPolicy` и RBAC; потом HPA и нагрузка; потом файлы окружений; потом аварийные проверки (плохой образ, удалённый Pod); в конце README. После **каждого** шага запускай `helm lint`, `helm template` и смотри `kubectl get pods`. Если что-то не работает, иди по чеклисту из шага 7.6 и таблице шага 8.6: Pod → Service → Ingress → приложение.

### result
Здесь нет запуска: это задание для самостоятельной работы. Когда закончишь, пройди таблицу приёмки и ответь на вопросы ниже. **Решения в лабе нет — и это нормально:** ты проверяешь себя сама, а не сверяешься с чужим файлом. Если хочешь получить разбор своей работы, пришли свою папку `final/`.

### why
Это та самая работа, ради которой писалась лаба: на входе — заказ на человеческом языке, на выходе — релиз, который можно поставить одной командой, проверить, обновить и откатить. Всё, что ты сделала здесь, — реальные задачи для любого сервиса в Kubernetes: доступность, данные, безопасность, масштабирование, воспроизводимая установка. Если справилась — ты готова к управляемому кластеру в облаке и к GitOps: там те же объекты, только кластер обслуживает провайдер, а выкатывает не человек, а контроллер.
